# Native attachment validation — follow-up to the scanner integration

Source work only. No feature flag, deployed binding, secret, DNS route, migration,
customer data or production deployment is changed by this patch. Keep PR #4 draft.
See `native-antimalware-rollout.md` for the existing service/gateway architecture.

## Corrected R2 adapter boundary

The transient download adapter previously used `{ ...object }` to copy an R2 object.
That loses metadata and the body when a binding exposes inherited/non-enumerable
accessors. A regression test using prototype accessors reproduced an incorrect
`503 attachment_storage_unavailable` both for a clean object and for quarantine.
The adapter now copies key, size, etag, version, checksums and body explicitly.
The actual received body is still tied to its version-specific scan receipt;
customer bytes and metadata are never rewritten. Tests keep this native-object
shape alongside the existing plain-object doubles so the regression cannot hide.

Private verdict receipts now also require their own native SHA-256, exact byte
length and key. Receipt contents are projected from the verified protocol fields;
unrecognized service diagnostics are not persisted. Old receipts written by the
previous scanner already include native checksums. Missing/corrupt receipts stay
untrusted and may be regenerated by the existing authenticated scan retry.

## Capability requires scanner reachability

After the existing bearer guard and configuration/schema checks, the capability
handler calls the fixed private `ANTIMALWARE` service's authenticated `/health`.
The probe has a two-second deadline and a 1 KiB JSON limit. An unavailable service,
401, redirect, HTML, malformed reply, delayed response or stalled stream returns
`attachments: false`. Response bodies are cancelled on timeout or rejection.

This is a readiness read, not an activation or a scan. It does not expose any
scanner diagnostic in the public capability response. The other file endpoints
keep their existing quarantine behavior; cached, valid scan receipts still work
without treating a scanner outage as an expired mobile token. The Vercel BFF's
independent hard-off guard remains untouched. `/health` reachability is not proof
of a safe loaded ClamAV configuration, supported engine or correct public routing.

## Executable controls for a real installed engine

`services/antimalware/verify_engine.py` uses the SAME `ClamD` implementation as the
HTTP scanner service. Its CLI connects only to an explicitly supplied local Unix
socket, and submits synthetic controls. It never fetches customer files or uses
CRM/R2 credentials. It does not install/reload a daemon or modify its settings.
The existing adapter checks the signature database freshness and version stability.

Run on an operator-approved scanner test host with the reviewed configuration,
current signature database, Python 3.11+ and the local `zip` utility:

```sh
python3 services/antimalware/verify_engine.py --socket /run/clamav/clamd.ctl
```

Required controls: clean text, exactly 20 MiB of clean bytes, the harmless EICAR
test signature, EICAR in a ZIP, an encrypted ZIP, a bounded archive with a 22 MiB
member (above the reviewed 21M extraction limit), and 12 nested archives (above
the reviewed recursion limit of 10). The last four blocked controls must produce
a definitive blocked verdict, not an exception falsely counted as a detection.
Encrypted fixture generation uses a fixed public test password, not a secret.
Temporary fixture files are removed on completion/error. Host antivirus may
intercept these harmless test files; that is not a successful daemon test.

Missing engine/socket, stale signatures, unavailable fixture tools, incomplete
control sets or unexpected results return a nonzero exit code and an expurgated
JSON report. No case is silently skipped. All seven controls must pass with a
consistent engine/signature version. These behavior checks do not authenticate
the daemon binary or prove the HTTP service, Cloudflare binding, public hostname,
iOS app or production restore. The report therefore keeps `productionVerified`,
`daemonBinaryProvenanceVerified` and `deployedRoutingVerified` false.

Official protocol and configuration references:
- https://docs.clamav.net/manual/Usage/ClamdProtocol.html
- https://github.com/Cisco-Talos/clamav/blob/main/etc/clamd.conf.sample
- https://developers.cloudflare.com/r2/api/workers/workers-api-reference/

## Evidence from this follow-up

The previous baseline was `5cac0d7542db29b7d12ed4938b2c1a6779fc53cf`.
The two inherited-accessor regression cases failed before the fix and pass after it.

- 39 Node tests passed: 22 existing scanner/receipt tests plus 17 new boundary,
  integrity and readiness tests. No failures or skips. SQLite runs the real
  0018/0019 SQL in memory. R2 and the scanner are controlled doubles, not live services.
  Route wiring tests inspect source; they do not authenticate real mobile sessions.
- 10 Python tests for the engine verifier passed. These test harness behavior,
  fixture construction and fail-closed reporting; they are NOT ClamAV detection tests.
- Strict isolated TypeScript checking passed against the existing D1/R2 interfaces.
  The local Node test loader only resolves TypeScript extensions; it replaces no
  application code. Python syntax compilation passed.
- The real-engine command was attempted in the execution container. It returned
  exit 1 with `daemon_unavailable_or_signatures_invalid` and no executed controls.
  ClamAV is absent here. No successful real-engine detection is claimed.
- Relevant fetched baseline files were checked against their Git blob hashes before
  modification/testing. Full dependency installation, full build/lint/suite were
  not run locally: direct GitHub/npm network resolution was unavailable.

Normal dependency-installed repository commands:

```sh
node --import tsx --test tests/mobile-antimalware.test.mjs tests/mobile-antimalware-boundary.test.mjs
python3 -m unittest discover -s services/antimalware -p 'test_verify_engine.py' -v
```

## Remaining deployment gates, not satisfied by these tests

The private scanner must be deployed and verified with real controls and freshclam;
the narrow same-host gateway must be wired to the identified existing CRM Worker
and validated with 20 MiB multipart/DNS64/IPv6/authentication; the Swift policy must
be wired into the real app, preserving local originals and IDs on 423; existing
D1/R2 exports must be restored on isolated real resources and checked against their
source inventory. The iOS repository was searched again through the GitHub
connection and its direct lookup still returned 404. No iOS source was modified.
No actual backup was provided or restored. Neither `engineControlsPassed` nor a
passing offline SQL/copy verifier alone authorizes enabling attachments.
